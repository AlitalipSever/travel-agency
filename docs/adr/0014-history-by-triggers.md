# 0014 Change history by database triggers, not an application audit log

Status: accepted (2026-10-27)
Date: 2026-10-27
Addresses: N2, L1, P1, P2, P3, P6 (audit criteria); 00-domain §2 (regulators)

## Context

Catalogue, departures, bookings, locations and bracket settings change over time and the
agency, its finance and any auditor need to know who changed what and when, and what a row
looked like at a given moment. SQL:2011 defines system-versioned tables for exactly this
(`FOR SYSTEM_TIME AS OF`); PostgreSQL has no native implementation.

## Options

1. Application level audit log: one table written by the service layer on every change.
   Simple; misses changes made through the admin, scripts or raw SQL unless every path is
   wired; no "as of" reads without extra work.
2. PostgreSQL extensions that emulate system versioning (`temporal_tables`, `periods`):
   closest to the standard; not available on most managed services, uneven maintenance.
3. Per-table history tables filled by database triggers, with the acting user and request
   attached from a session variable set by the application (`django-pghistory`): catches
   every write path, gives "as of" queries, no extension needed.

## Decision

Option 3. Tracked models get a history table and triggers generated by migrations; a
middleware sets the user and request context per transaction so each history row knows its
actor. History tables do not count toward the model's readability budget (N2.8). Reads: a
row "as of" a time, and the actor of any change.

## Consequences

A small write overhead on tracked tables. History grows with changes, not with reads; no
pruning in this iteration. The earlier "one audit table" wording in architecture §8 is
replaced by this decision. Native system versioning, should PostgreSQL gain it, would be a
drop-in replacement for the same requirements.
